# Research behind the method

Each source and what it changed. Only techniques that improve this method are kept; heavier tools are named with when they are overkill.

| Technique | Source | What it changed here |
|---|---|---|
| Characterization testing | Michael Feathers, *Working Effectively with Legacy Code* (2004), ch. 13; [Characterization Testing](https://michaelfeathers.silvrback.com/characterization-testing) | The base run records what the system **actually** does ("a system in production becomes its own specification"), not what the ticket says. The table has separate base and PR columns, and the expected value comes from reading base code. |
| Golden master / approval testing | [ApprovalTests](https://approvaltests.com/) | Same idea as a stored artifact. Not adopted as a tool: a sandbox run's output carries ids and timestamps that change every run, so the scenario table is the approved artifact, reviewed by a human. |
| Differential / back-to-back testing | W. M. McKeeman, "Differential Testing for Software", *Digital Technical Journal* 10(1), 1998 (bibliography; not re-read) | Names the core: two versions, same input, compare outputs. |
| Noise filtering in diffs | [Diffy](https://github.com/opendiffy/diffy): primary and secondary run the same known-good code; their disagreement rate is the noise floor for primary vs candidate | The **noise baseline**: re-run the same version on the same data; anything that changes there is not a PR difference. Normalize ids and timestamps. |
| Shadow / experiment in production | [GitHub Scientist](https://github.com/github/scientist): "only safe for wrapping methods that aren't changing data"; blocks run in random order, so shared data can change between them | Writes make order matter: a fixed **PR-first, base-second** order for vendor writes, and an explicit `not seen: consumed by the PR run` cell instead of a false mismatch. |
| Dark launching | Martin Fowler, [DarkLaunching](https://martinfowler.com/bliki/DarkLaunching.html) | Out of scope: it runs new code on real users' traffic. Here no real person is ever reachable; that is the point of the safety gate. |
| Contract testing | Martin Fowler, [ContractTest](https://martinfowler.com/bliki/ContractTest.html); [Pact: what it is good for](https://docs.pact.io/getting_started/what_is_pact_good_for) | Pact does not fit third-party vendors ("consumers cannot be individually identified", provider state only through the API under test). A sandbox run is the contract check for hand-typed vendor types and test doubles: a mismatch is a finding to feed back into the types and the vendor notes, not just a red cell. |
| Record and replay (VCR) | Martin Fowler, [SelfInitializingFake](https://martinfowler.com/bliki/SelfInitializingFake.html); [vcrpy](https://vcrpy.readthedocs.io/en/latest/advanced.html) (`filter_headers`, `filter_sensitive_data`) | Optional: record the vendor **reads** of the first run and replay them for the second, so both see identical input when sandbox state drifts. Overkill for most runs; never replay writes. Cassettes must filter auth headers and are sandbox data only. |
| Mutation testing | G. Petrović, M. Ivanković, [State of Mutation Testing at Google](https://research.google/pubs/state-of-mutation-testing-at-google/), ICSE-SEIP 2018: mutants only on changed, covered lines, surfaced in code review | The mutation check targets only the lines the PR changed. A full mutation tool (Stryker, PIT) is overkill for one PR. |
| Time-dependent code | Martin Fowler, [ClockWrapper](https://martinfowler.com/bliki/ClockWrapper.html) | Clock injection for unit tests. For a sandbox run, move dates in the local data and run the job directly; faking the process clock also moves token expiry and TLS validity. |
| Test isolation and shared fixtures | Gerard Meszaros, *xUnit Test Patterns* (2007), "Erratic Test" causes: Interacting Tests, Test Run War (bibliography; not re-read) | A deployed environment sweeping the same sandbox is a Test Run War you cannot stop: record its effects, do not fight them. Local prep marks old records processed so runs do not interact. |
| Safe outbound side effects | [Twilio test credentials](https://www.twilio.com/docs/iam/test-credentials) (example: test credentials never deliver) | Use a vendor's test mode where it exists. Where the vendor itself sends, only a fail-closed stub (allowlisted reads, everything else throws) in every process that runs the code is safe. |
